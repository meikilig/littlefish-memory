# 03 · 取舍

这一份记的是"为什么长成这样"，以及踩过的坑。代码里读不到的东西都在这里。

## 为什么分四级，而不是"重要 / 不重要"两档

两档的问题是它只有一个维度：重要。但真实场景里有两个维度——**多重要**（印象分）和**还记不记得**（新鲜度）。一条"主人说过不许熬夜"很重要，但三个月没提起过，它还该占 2200 字预算的一格吗？四级就是把这两件事拆开：L4 保重要性（永不降级），L1/L2/L3 保新鲜度（会往下掉）。

L4 的"不设上限"是明确的取舍：**存储不设限，注入设限**。刻下的条目可以无限多，但注入仍然只有 2200 字，装不下就只留标题。这样"她记得"这件事不会被预算挤掉。

## 为什么 hits 是新加的一列，不是复用旧的计数

旧列叫 `recall_count`，语义是"这句话被重复说了几遍"。实测里有一条 `'那这个说来话长了…'` 记了 56 次——那是一句口头禅，不是被想起 56 次。拿它当升级依据，等于奖励废话。

所以四级上线时新加了 `hits` / `last_hit_at`，只由 `recall.on_message` 在**检索真的命中了**才 +1。旧的 `recall_count` 保留但不再参与任何判定。

## 为什么"升级"还要看"最近"

这一条是实测踩出来的：`sweep()` 按 `hold_days` 把一条旧事降到 L1，同一次扫描的末尾 `promote_by_hits()` 又按累计 hits 把它提回去——**降级永远不生效**。修法是把时间窗写进 `_want()`：够线还不够，还得"最近 N 天内被想起过"。看上去是加了条件，实际是让"降级"这个动作真正有后果。

## 为什么 `<recall>` 要单独一段，而且只有 200 字

"被想起"如果只是记账（hits+1、tier 升级），那它就是个后台计数器——她并不会真的"想起来"。但它也不能大：塞多了会挤掉七桶，而且每轮都塞同样的东西就等于没塞。

所以：只在**这一轮真的命中**时才出现，放在记忆块**前面**（先看到"刚想起的"，再看"平时记得的"），限 200 字，并且开头就写明"这是刚才想起的过去的事，**不是现在要你做的事**"——否则那些带祈使句的原话会被当成本轮指令。

### 踩过的坑：命中但没装下

第一版把"所有命中的 id"都从七桶里剔掉，结果预算装不下、没进 `<recall>` 的那几条既不出现 `<recall>` 里、也不出现在任何桶里——**这一轮彻底消失**。修法是 `_recall_block()` 返回"真正装进去了的 id 集合"，只剔这些。

## 为什么私聊隔离是硬编码的，不做成开关

所有私聊的 `group_id` 都是空串。早期 `scene_ok()` 只看 `group_id`，于是"好友的私聊"能读到"主人私聊的记忆"——不是权限问题，是字段根本没区分。修法是在 `scene_ok()` 里加一条不归任何开关管的规则：两边都认得出 `conversation_key` 就必须完全相同。做成开关反而危险，谁手一滑就串味了。

配套的是 `<rooms>`：只列"哪扇窗最近有过动静、叫什么名字、多久以前"，**一句原话都不给**。她可以知道"我和那个人聊过"，但不能把那边的话带过来。

## 为什么白天流水不注入

白天说的话如果每条都进上下文，等于把整天的对话重放一遍，预算瞬间爆掉，而且信息密度极低。所以流水只作"今天发生过什么"的材料，夜里复盘时提炼成几条记忆（默认最多 6 条"学到的"+ 2 条"要改的"）。

代价是：**当天她说的话，当天不会以"记忆"的形式回来**。这是故意的——当天的事还在上下文里，不需要再从库里捞。

## 为什么档案室按"一天一页"，而不是按对话

按对话切会把一天拆成几十页，目录没法扫；按天切一页正好是"那天发生了什么"的最小单位，也是人回想时的单位（"十月三十一号那天"）。页里的原话不删，只增；索引方向是"词 → 页"，查询方向是"日期 / 词 → 页"。

### 踩过的坑：日期不在索引里

第一版只走 bigram 倒排。用户问"十月三十一号那天的原话"，倒排里没有"日期"这个概念，于是撞到 10-30 的页，她念出来的"最后两句"其实是前一天的。修法是加 `parse_day()`：认 `2026-10-31` / `10月31日` / `十月三十一日` / `10-31` / `昨天`，认出来就直接按 `day` 精确取页，根本不走模糊。

### 踩过的坑：长页只给开头

"把你说的最后两句念给我听"——只给开头就永远答不了。改成头 2/3 + 尾 1/3。

## 为什么"记忆搜不到才去翻档案"

反过来（先翻档案）会让每轮都去扫一遍大表，而且档案是原文，塞进上下文太贵。现在的顺序：先记忆（短、提炼过、便宜），记忆里有就直接答；记忆里没有、或者问题里带了明确的时间/出处线索（"那天""原话""档案室"）才追加档案目录。

## 故意的没做

- **向量检索**：现在的 bigram 倒排零成本、可解释、能离线跑。向量检索的代价是每次都要调模型或本地模型，收益是"换个说法也能搜到"。这条留给人自己决定。
- **阶段③ 日结全量**：白天流水已经只进本子，但"晚上挑几条"的挑选质量还是天花板。
- **产物索引**：记忆的 `ref` 现在还指不回档案页码 / 书桌本子页。要做成"她发现记忆里没有，就去档案室找"的完整闭环，这一步是必须的，但会牵动整个引用体系，没在这次抽库里做。
- **失败重试 / 幂等**：`build_day` 是幂等的（同一天同一窗同一类只更新不新增），但抽取流水失败时没有重放队列 —— 靠每天再跑一次兜。
